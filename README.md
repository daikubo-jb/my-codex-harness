# my-codex-harness

Codexで日常の開発作業を進めるための個人用設定一式です。メインエージェントが作業を最後まで所有し、必要な場合だけ計画レビュー・テスト支援・完成物レビューを使います。リポジトリをマスターとして管理し、`install.sh`でCodexの共通指示、カスタムエージェント、Skillsへシンボリックリンクを張ります。

MIT Licenseで公開しています。これは汎用的なハーネスの土台であり、個人の`~/.codex`設定、hook/rules、doc-storageの実データは含めません。

このリポジトリに記載されたモデル名は、利用するCodex環境で使用可能とは限りません。導入前に`agents/*.toml`の`model`を環境に合わせて確認・変更してください。`DOC_STORAGE_ROOT`も自分の環境に合わせて設定します。

## 全体像

```text
依頼
  ↓ 目的・受け入れ条件・リスクを確認
メイン: 探索 → 必要な計画 → 実装 → 検証 → 修正
  ├─ 未確定の成果物判断 → spec
  ├─ 難しい局所判断 → advisor (read-only)
  ├─ 高影響な境界判断 → senior-advisor / Astra (read-only)
  ├─ 高リスクの計画 → plan-reviewer
  ├─ 大量ログ・独立検証 → test-runner
  └─ 中規模・高リスクの完成物 → code-reviewer (read-only)
  ↓
受け入れ条件・検証結果・最終差分を照合して完了または残課題を報告
```

小さな可逆変更に手続きを強制しません。API互換性、DB移行、認証・認可、秘密情報、不可逆な変更では、影響・移行/rollback・検証方法を計画し、必要なレビューを行います。レビュー後に修正したら、影響する検証を再実行します。

## 構成

```text
AGENTS.md                  共通原則、条件付きフロー、完了契約
agents/                    カスタムサブエージェントのTOML定義
agents/README.md           Agentのモデル・権限・役割一覧
skills/                    Codex Skills（`harness-review`は明示起動専用）
scripts/verify-harness.sh  設定と導入の再現可能な検証
install.sh                 個人環境へのシンボリックリンク
LICENSE                    MIT License
.gitignore                 ローカル生成物と環境ファイルの除外
```

`AGENTS.md`は地図と共通契約に留め、Skillやエージェント固有の手順を重複させません。独自のオーケストレーター、モデル自動選択、Advisorの階層はこの版には含めません。既存のCodex sandbox・権限設定を利用し、プロンプトの禁止だけを安全機構とはみなしません。

言語は用途で分けます。ユーザー向けの最終回答は日本語とし、Agent間の構造化出力を導入する場合は項目名・状態名・識別子を英語にできます。推論言語の固定やchain-of-thoughtの出力は要求しません。

Agentごとのモデル、推論強度、sandbox、役割は[agents/README.md](agents/README.md)にまとめています。設定の正本は各`agents/*.toml`であり、一覧は検証スクリプトで定義と照合します。

## 導入

まず`skills/doc-storage/SKILL.md`の`DOC_STORAGE_ROOT`を自分の環境に合わせ、必要ならdoc-storageの枠を作ります。その後、リポジトリのルートで次を実行します。

```sh
cd /path/to/my-codex-harness
./install.sh
```

インストール先は`${CODEX_HOME:-$HOME/.codex}/AGENTS.md`、`${CODEX_HOME:-$HOME/.codex}/agents/`、`$HOME/.agents/skills/`です。同名の通常ファイルは`.bak.<日時>`へ退避してからリンクします。既存の利用環境を変更するため、初回は内容を確認してから実行してください。現在の`install.sh`はCodexのグローバルhook/rulesを変更しません。

公開リポジトリへ導入する場合も、`AGENTS.md`やworklogにAPIキー、顧客情報、社内パス、個人の設定値を記録しないでください。worklogを別のサービスやモデルへ読ませる運用では、必要に応じて秘密情報と個人情報を伏せ字にします。

## 使い方

```text
$spec 通知機能を作りたい
$feature /path/to/approved-plan.md
$plan-review
$doc 今回の設計判断、検証結果、残作業
$harness-review [対象期間や対象プロジェクト]
```

小さな変更はSkillを使わず、対象ファイルと完了条件を直接依頼します。`$feature`は中規模以上で使い、計画・レビュー・test-runner・記録を変更の性質に応じて選びます。`$spec`はユーザーの選択が成果物を変える未確定の大きな依頼だけで使います。`$harness-review`は月1回または10セッションごとを目安に手動で起動し、運用ログから改善候補を提案します。

## シナリオ別フロー

| シナリオ | 期待する進め方 |
| --- | --- |
| 局所的・可逆な変更 | メインが実装し、関連検証と差分確認を行う。spec、plan-reviewer、test-runner、記録は必須にしない。 |
| 通常の複数箇所機能 | 必要なら短い計画を作り、実装・検証・完成物レビューを行う。指摘を修正したら再検証する。 |
| 難しい局所判断 | repoの証拠を確認してもtrade-offが残る場合にadvisorへ相談し、助言を証拠・テストと照合して採否を決める。 |
| DB移行・API互換性・認証変更 | 影響、互換性、移行またはrollback、検証方法を計画し、plan-reviewerとcode-reviewerを使う。システム境界やrollbackコストの判断が残る場合だけsenior-advisorを使う。 |
| 検証環境が不足 | 未実行の理由と再開条件を示し、完了扱いにしない。 |
| レビュー後に修正 | 修正の影響する検証を再実行し、最終差分と受け入れ条件を再確認する。 |
| 別モデル・別セッションで再開 | 現在のブランチと差分を作業記録に照合し、残作業と次の操作から再開する。 |

## 検証と保証範囲

対象プロジェクトの`AGENTS.md`、`CLAUDE.md`、`.agents/skills/run-*`、既存設定、CIの順に検証方法を探します。結果は成功・失敗・未実行・対象外を区別し、必須検証の未実行や失敗を完了扱いしません。

このリポジトリ自身の設定検証は次で実行できます。

```sh
bash scripts/verify-harness.sh
```

この検証はTOML/frontmatter/参照整合、Agent一覧との設定一致、明示起動専用Skillのポリシー、シェル構文、隔離した`install.sh`の全リンクと退避を確認します。実際のCodexセッションでエージェントが期待どおり委譲されること、品質・速度・コストが改善することは自動保証しません。運用評価では、code-review後の修正件数、同じ問題の再発、再試行回数、hook/rulesの摩擦、所要時間と利用量を同じ代表タスクで比較してください。

この版では、CodexのグローバルStop hookとrulesは自動導入しません。まずworklogを収集し、`$harness-review`で候補を確認してから、必要なリポジトリだけへ段階的に導入します。

## 公開・再利用時の注意

- `LICENSE`はMITです。著作権表示を変更する場合は、公開前に`LICENSE`とこのREADMEを合わせて更新してください。
- `agent_harness_design_spec.docx`は設計原資料です。公開対象に含めるかは、本文の公開範囲とバイナリ配布の必要性を確認してから決めてください。
- `agents/*.toml`は実行環境のモデル、sandbox、利用可能な権限に依存します。公開先の利用者がそのまま実行できることを保証しません。
- `install.sh`は既存の同名ファイルをバックアップしてリンクへ置き換えます。自分の環境に合わせて内容を確認してから実行してください。

## ドキュメント

リポジトリ内で文書を管理する慣習がないプロジェクトでは、`<DOC_STORAGE_ROOT>/<project>/codex-doc/`に計画、レビュー、調査、作業記録、判断を保存します。長時間・高リスク・引き継ぎが必要な作業では、対象リポジトリ、ブランチ/コミット、目的、完了条件、決定事項、検証結果、未解決事項、次の操作を記録します。小変更の記録は必須ではありません。

作業記録のworklogには、末尾に固定の「ハーネスへの示唆」欄を置きます。指示の不備、hook/rulesの拒否や摩擦、advisor/reviewerの指摘と採否を、推測ではなく発生事実として記録します。ハーネス自体の変更は`$harness-review`で候補を出し、ユーザーが選択した後に行います。
